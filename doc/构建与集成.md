# tags-wasm 构建与集成

> **覆盖**：crate 结构、导出的 WASM 函数、构建流程、两个前端各自的消费方式。
> **不覆盖**：标签业务的数据库结构与权限 → [backend_73info/doc/数据库Schema.md](../../backend_73info/doc/数据库Schema.md)；前端如何渲染标签树 → [user-client/doc/架构.md](../../user-client/doc/架构.md)。
> 上级约定：[AGENTS.md](../../AGENTS.md)

## 一、crate 结构

```
tags-wasm/
├── Cargo.toml      crate-type = ["cdylib", "rlib"]
├── Cargo.lock
├── src/lib.rs      唯一源文件
└── pkg/            wasm-pack 产物（被 .gitignore 忽略，不入库）
```

edition 2021，唯一的运行时依赖是 `serde`（配合 `serde-wasm-bindgen` 与 `wasm-bindgen` 做 JS 值转换）。`cdylib` 用于产出 WASM，`rlib` 让它同时能被 Rust 侧引用。

## 二、导出的函数

`src/lib.rs` 里挂了两个 `#[wasm_bindgen]` 入口，输入输出都是 `JsValue`，内部由 `serde_wasm_bindgen` 在 JS 值与 Rust 结构之间转换：

| 函数 | 用途 |
| --- | --- |
| `process_tags` | 面向用户端的标签处理，返回标签树 |
| `process_admin_tags` | 面向管理端的标签处理，返回管理态标签树 |

两者共用同一套内部逻辑，差别只在入口形态——所以改标签处理规则时，**两个入口都要确认**，别只改一个。

失败时返回 `Err(JsValue)`，JS 侧表现为抛出的异常；调试时先看异常字符串。

## 三、构建

改动 `src/lib.rs` 后必须用 `wasm-pack` 重新构建，产出 `pkg/`：

```bash
cd tags-wasm
wasm-pack build
```

- `pkg/` 在 `.gitignore` 里，**不入库**。
- 仓库里**没有**放构建脚本或 `package.json`，所以没有 `pnpm build:wasm` 这类快捷命令，需要手动执行 `wasm-pack`。
- 现有 `pkg/` 是 wasm-pack 默认的 bundler 形态：`package.json` 里 `main` 指向 `tags_wasm.js`、`type: "module"`、没有 `module` 字段，另含 `tags_wasm.d.ts`、`tags_wasm_bg.wasm`、`tags_wasm_bg.wasm.d.ts`。
- 构建环境需要 `wasm-pack` 与 `wasm32-unknown-unknown` target（`rustup target add wasm32-unknown-unknown`）。

## 四、前端如何消费

| 前端 | 依赖写法 |
| --- | --- |
| `user-client` | `"tags-wasm": "link:../tags-wasm/pkg"` |
| `admin_client` | `"tags-wasm": "file:../tags-wasm/pkg"` |

两者都装了 `vite-plugin-wasm` 来处理 `.wasm` 的加载。注意一个是 `link:`（软链到源目录，改完 `pkg/` 立刻可见）、一个是 `file:`（安装时拷贝一份），**`admin_client` 在重建 `pkg/` 后可能需要重新 `pnpm install`** 才能拿到新产物。

## 五、两条顺序约束

1. **改了 Rust 源码 → 必须重建 `pkg/`，前端才生效。** 只改 `src/lib.rs` 不重建，前端跑的还是旧 WASM，表现为「代码明明改了却没反应」。
2. **新克隆仓库 → 先构建 `pkg/`，再 `pnpm install`。** `pkg/` 不在仓库里，前端在 `pnpm install` 阶段解析这个依赖，顺序反了会解析失败。
